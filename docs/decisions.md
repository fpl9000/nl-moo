# Decisions

A running log of decisions about NL-MOO's implementation, newest milestone last. Each entry says what was decided, when, and why, and points to the plan item (in [`nl-moo-implementation-plan.md`](../nl-moo-implementation-plan.md)) or design section (in [`llm-moo-design-v2.md`](https://github.com/fpl9000/ai-docs/blob/main/llm-moo-design-v2.md)) it settles. Proposed answers to the plan's section 5 specification gaps are added here in the pull request of the milestone that first needs them, so each one is reviewed where it matters.

## Settled before M0

- **Repository and naming (plan A1), Nov 16, 2026.** The code lives in the public repository `fpl9000/nl-moo` with Go module path `github.com/fpl9000/nl-moo`. The executable is `nl-moo`, built from `cmd/nl-moo`, rather than the design's `moosd` (§14.1), and the design's `moosd.toml` config file (§14.4) correspondingly becomes `nl-moo.toml`.
- **License (plan A1), Nov 16, 2026.** AGPLv3. Section 13 of that license obliges anyone running a modified server for network users to offer them its source, so M6 adds a login banner with a configurable source link.
- **Platforms (plan A2), Nov 16, 2026.** Windows first, and the server must keep working on Linux. CI therefore tests every change on both, and platform-specific code will be confined to one small package with build-tagged files per operating system. TLS stays at M15 unless the server is exposed beyond the local machine sooner.
- **API key handling (plan A3), Nov 16, 2026.** `nl-moo.toml` names the environment variable that holds the Anthropic API key (for example `api_key_env = "ANTHROPIC_API_KEY"`) and never holds the key itself, so the key cannot be committed to the repository. The plan suggests that an unset or empty variable starts the server in `mechanical_only` mode with a log message rather than refusing to start; that detail is implemented, and can be revisited, at M8.
- **Interim `@program/raw` (plan C1), Nov 16, 2026.** A wizard-only `@program/raw <obj>.<method>` command arrives at M7, so natural-language methods can be installed and tested before the Programmer agent exists (M14). It stays afterwards as a power-user tool. This is an approved deviation from §11.1.

## M0

- **Go version.** `go.mod` requires Go 1.27, the current stable release. CI installs the newest 1.27.x patch release on every run, so standard-library security fixes, which `govulncheck` would otherwise flag, arrive without a code change. Moving to a newer Go release is a deliberate one-line change to `go.mod` in its own PR.
- **License file.** The repository was created with the GPLv3 text in `LICENSE`. M0 replaces it with the verbatim AGPLv3 text to match the A1 decision above.
- **Pinned analysis tools.** CI installs fixed versions of `staticcheck` and `govulncheck` (set at the top of `.github/workflows/ci.yml`), so a new release of either tool cannot turn CI red unannounced; upgrades happen in a PR.
- **Version reporting.** `nl-moo -version` prints a version string (`dev` unless set at build time with `-ldflags "-X main.version=..."`), the git commit the binary was built from when the go command recorded one, the Go version, and the target OS and architecture. The commit makes every build traceable to a checkpoint.

## M1

Settled while building the object model (`internal/world`). Items marked **(review)** are choices where the design is silent or ambiguous and a different answer would change later milestones; the rest follow the design or LambdaMOO directly.

- **Formats left uninterpreted.** Where a later milestone defines a format, M1 stores the raw value and checks only that it is well-formed: a method's `Rule` (the `MechanicalRule`, design §17 item 9, to be settled with Fran before M5) and `Contract` (the `EffectContract`, M2) are raw JSON, its `Signature` (plan B2) is a string, its `Reads` selectors (plan B3) are strings, and a property's `Schema` is raw JSON that nothing enforces until M2. Keeping `Contract` as raw JSON also avoids an import cycle, because `internal/contract` will import `internal/world`.
- **Object IDs.** `ObjID` is a signed 64-bit integer, matching SQLite's INTEGER, with `Nothing` = `#-1`. `PlayerID` is a type alias for `ObjID` that documents intent. IDs are allocated from `#0` upward and never reused; a failed `Create` does not consume an ID.
- **A vehicle flag (review).** §6 lets players be inside objects "flagged as a vehicle", but §4.1's flag list has no such flag, so `FlagVehicle` is added. The flag bit positions (player, room, exit, wizard, fertile, frozen, vehicle, lowest bit first) are fixed from now on, because M3 persists them in `objects.flags`.
- **Object references inside JSON values (review).** §4.2 lists "ObjID ref" as a value type but does not say how it is written in JSON. M1 treats a JSON string that is exactly an object ID in canonical notation (`"#1023"`, no leading zeros) as a reference, the same notation effects documents (§7.3) and `@set` (§12.2) use; `"#-1"`, map keys and strings that merely contain an ID are not references. Every write must reference only live objects: recycled IDs are refused (§6) and so are IDs not yet allocated, which would otherwise start naming whatever object later receives that ID. Values already stored that name an object recycled afterwards are tolerated, as in LambdaMOO. The alternative is a tagged form such as `{"$ref": 1023}`, which is unambiguous but heavier for the model to write. This should be confirmed before M3 persists values.
- **The `c` bit and ownership of inherited slots (review).** §4.2 defines `c` as "value is copied to children on creation", while LambdaMOO's `c` means "the child's slot is owned by the child's owner". M1 does both: when a child is created, each inherited property with `c` is copied into a local slot on the child, owned by the child's owner. A property without `c` is not copied; the child sees the ancestor's value live, and the inherited slot keeps the defining property's owner. Writing such a property on the child creates an override slot on the child with the inherited owner, permissions and schema, and never changes the ancestor (LambdaMOO's behavior). The effect is that a prototype can keep state on its children that the children's owners cannot tamper with, unless the prototype marks it `c`.
- **Property access follows the property's owner, not the object's.** Read and write checks use the owner of the slot that lookup finds, as in LambdaMOO, so a wizard-owned property on a player's object is out of that player's reach without the `r` or `w` bit. Changing a property's permissions or schema needs its owner or a wizard; `@chown` of anything is wizard-only (§4.4).
- **Reserved names.** `name`, `aliases`, `location`, `contents`, `parent`, `owner` and `flags` cannot be defined as properties, because selectors and §4.2's built-ins already give them meaning. Anyone may read them; `name` and `aliases` are writable by whoever controls the object; the rest change only through their own operations (move, chparent, chown, flag changes). `description`, `home` and `quota` are ordinary properties that the bootstrap database (M3) defines on the prototypes. A property name is defined once along any parent chain; a child may hold its own value for an inherited property, which is an override rather than a second definition.
- **Methods are programmed by their owner.** Adding a method to an object (including an override of an inherited one) needs control of the object; changing a method the object already has needs that method's owner or a wizard, so a wizard's method installed on a player's object stays the wizard's. On a `Frozen` object only wizards may program methods (§4.1); freezing stops edits, not calls, and does not affect properties. The design has no method `r` bit, so nothing yet governs who may read a method's body; that comes with `@program` and `@show`.
- **Who may set which flag (review).** `Player`, `Wizard` and `Frozen` are wizard-only (§4.4, §4.1; `Player` as in LambdaMOO, since it confers the ability to own things). `Fertile`, `Room`, `Exit` and `Vehicle` may be changed by whoever controls the object. Separately from permissions, three invariants hold for everyone: the `Player` flag never changes after creation (ownership rests on it, and player creation and quotas come later), only players may be wizards, and an object with players directly inside it must stay a room or a vehicle.
- **Root objects are wizard-only (review).** Only wizards may create an object with no parent. LambdaMOO lets any programmer do so, but a root object inherits none of the audited prototype behavior, so the conservative choice is taken for now.
- **Authority.** Every permission check takes the principal explicitly. A principal must be a live player at the moment of the check, so a method whose owner has been recycled can do nothing, and a wizard who loses the flag loses wizard powers immediately. A method runs as the owner of the method that lookup finds, which may live on an ancestor (§4.4).
- **Moving needs control of the moved object only.** The destination's owner is not consulted, which is what makes §4.4's vending machine work. Players may be in rooms, in vehicles, or nowhere (`#-1`); "nowhere" is allowed because LambdaMOO puts new and disconnected players there.
- **Parent chains must be acyclic.** Not listed among §6's invariants, but implied by inheritance; `Load` rejects a loop, and lookups refuse to walk one rather than hang.
- **In-memory mutators (scope note).** M1 includes `Create`, `Move`, `SetFlags`, `DefineProp`, `SetProp` and `SetMethod`, because the invariants and the `c` bit cannot be tested without a way to change the world. They enforce invariants and check no permissions; the M4 engine will call them on its writer goroutine. `Load` builds a world from saved objects (for M3) and rejects any that break an invariant, rebuilding `Contents` in ID order. Recycling, re-parenting and chown have their permission rules in `perms.go` now, but their mutators arrive with `@recycle`, `@chparent` and `@chown` at M7, where their remaining semantics (what happens to a recycled object's contents and children, for example) are decided.
- **Method defaults.** An empty care level becomes `normal` and a zero budget becomes 4, the §5 defaults.
